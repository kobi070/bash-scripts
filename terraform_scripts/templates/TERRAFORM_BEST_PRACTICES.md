# Terraform Best Practices — AI Context

> Use these rules when writing, reviewing, or refactoring Terraform code in this project.
> Follow them by default. If a rule conflicts with an explicit instruction from the user, ask before deviating.

---

## 1. Project Structure

- Separate **reusable modules** from **environment root modules**:
  ```
  terraform/
  ├── modules/                # reusable, versioned, no backend, no provider config
  │   └── <module-name>/
  │       ├── main.tf
  │       ├── variables.tf
  │       ├── outputs.tf
  │       ├── versions.tf
  │       ├── locals.tf       # optional
  │       ├── data.tf         # optional
  │       ├── README.md       # generated by terraform-docs
  │       ├── examples/
  │       └── tests/          # *.tftest.hcl
  └── live/                   # root modules, one state per directory
      ├── dev/
      │   └── <stack>/
      │       ├── main.tf
      │       ├── backend.tf
      │       ├── providers.tf
      │       ├── variables.tf
      │       ├── outputs.tf
      │       ├── versions.tf
      │       └── terraform.tfvars
      ├── staging/
      └── prod/
  ```
- Standard file layout in every module: `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf`. Split `main.tf` by concern (`iam.tf`, `network.tf`, `s3.tf`) once it exceeds ~200–300 lines.
- **One state per environment per stack.** Prefer separate directories per environment over Terraform CLI workspaces for isolating environments — directories make the target explicit and allow different backends/credentials per environment.
- Keep stacks small and scoped by lifecycle and blast radius (e.g., network, IAM, data, compute). A change to app infra should never require planning the VPC.
- Never put `provider` blocks or `backend` blocks inside reusable modules.

## 2. Versioning & Pinning

- Pin Terraform and providers in `versions.tf`:
  ```hcl
  terraform {
    required_version = ">= 1.10, < 2.0"

    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 5.0"
      }
    }
  }
  ```
- **Root modules:** pin providers with `~>` (pessimistic constraint) and commit `.terraform.lock.hcl`.
- **Reusable modules:** declare the *minimum* compatible version (`>= 5.0`) — let root modules decide the upper bound.
- Pin module sources to a tag or exact version, never a branch:
  ```hcl
  source  = "git::https://gitlab.example.com/infra/modules.git//vpc?ref=v1.4.2"
  # or registry
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.8.1"
  ```
- Generate lock file hashes for all platforms CI and developers use:
  `terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 -platform=windows_amd64`
- Upgrade providers deliberately in a dedicated change, read the changelog, and review the plan.

## 3. State & Backends

- **Always use a remote backend** with encryption and locking. Never commit `*.tfstate`.
- AWS S3 backend (Terraform ≥ 1.10 supports native S3 locking — DynamoDB no longer required):
  ```hcl
  terraform {
    backend "s3" {
      bucket       = "org-tfstate-prod"
      key          = "network/terraform.tfstate"
      region       = "eu-west-1"
      encrypt      = true
      use_lockfile = true
    }
  }
  ```
- State bucket: versioning ON, encryption (SSE-KMS) ON, public access blocked, access restricted by IAM, lifecycle rule for old versions.
- Treat state as **sensitive** — it contains secrets in plaintext. Restrict read access as tightly as write access.
- Use partial backend config (`-backend-config=...`) when the same code targets multiple environments.
- Share data between stacks via `terraform_remote_state` sparingly, or better, via data sources / SSM Parameter Store / explicit outputs. Avoid tight coupling between stacks.
- Never edit state by hand. Use `terraform state mv`, `terraform state rm`, `import` blocks, and `moved` blocks.
- Never run `terraform force-unlock` without confirming no other run is active.

## 4. Naming Conventions

- Use `snake_case` for all resource names, variables, outputs, locals.
- Resource names describe role, not type — no repetition:
  - ✅ `aws_s3_bucket.artifacts`
  - ❌ `aws_s3_bucket.s3_bucket_artifacts`
- Use `this` for the single primary resource of a type in a module (`aws_iam_role.this`).
- Use plural names for collections (`var.subnet_ids`, `aws_subnet.private` with `for_each`).
- Build cloud resource names from a consistent prefix in `locals`:
  ```hcl
  locals {
    name_prefix = "${var.project}-${var.environment}"
  }
  ```
- Boolean variables are positive and prefixed: `enable_*`, `create_*`, `is_*`.

## 5. Variables

- Every variable has `description` and `type`. Add `default` only when a sensible default exists.
- Use precise types — avoid `any`:
  ```hcl
  variable "subnets" {
    description = "Map of subnet name to configuration."
    type = map(object({
      cidr_block = string
      az         = string
      public     = optional(bool, false)
    }))
  }
  ```
- Add `validation` blocks for constrained inputs:
  ```hcl
  variable "environment" {
    description = "Deployment environment."
    type        = string
    validation {
      condition     = contains(["dev", "staging", "prod"], var.environment)
      error_message = "environment must be one of: dev, staging, prod."
    }
  }
  ```
- Mark secret inputs `sensitive = true`.
- Use `nullable = false` when null is never valid.
- Keep the module interface small. Expose what callers genuinely need to vary; hardcode secure defaults.
- Don't pass entire environment configs as one giant object — prefer explicit variables.

## 6. Outputs

- Every output has a `description`.
- Output IDs, ARNs, names, and endpoints that consumers need — not entire resource objects.
- Mark outputs containing secrets `sensitive = true`.
- Don't output values that only exist for debugging.

## 7. Locals

- Use `locals` to name computed values and remove repetition, not to hide simple expressions.
- Define common tags once:
  ```hcl
  locals {
    common_tags = {
      Project     = var.project
      Environment = var.environment
      ManagedBy   = "terraform"
      Repository  = var.repository
      Owner       = var.owner
    }
  }
  ```

## 8. Resources & Meta-Arguments

- **Prefer `for_each` over `count`** for collections. `count` reorders/destroys resources when list items shift; `for_each` keys are stable.
- Use `count` only for conditional creation of a single resource:
  ```hcl
  count = var.create_bucket ? 1 : 0
  ```
- Key `for_each` maps by stable, human-meaningful identifiers — never by values known only after apply.
- Use `depends_on` only for hidden dependencies Terraform can't infer. Prefer implicit references.
- Use `lifecycle` intentionally:
  - `prevent_destroy = true` on stateful critical resources (databases, state buckets, KMS keys).
  - `create_before_destroy = true` for zero-downtime replacement.
  - `ignore_changes` only with a comment explaining why (e.g., autoscaling-managed `desired_count`).
- Use `precondition` / `postcondition` blocks and `check` blocks to assert assumptions.
- Prefer `dynamic` blocks only when the nested block count is genuinely variable; don't use them to look clever.
- Avoid `null_resource` / `local-exec` / `remote-exec` provisioners. Use native resources, `terraform_data`, cloud-init, or configuration management instead. Provisioners are a last resort.

## 9. Refactoring Safely

- Use `moved` blocks when renaming resources or moving them into modules — no manual state surgery:
  ```hcl
  moved {
    from = aws_s3_bucket.old_name
    to   = aws_s3_bucket.artifacts
  }
  ```
- Use `import` blocks (with `terraform plan -generate-config-out=generated.tf`) to adopt existing resources.
- Use `removed` blocks to stop managing a resource without destroying it.
- Every refactor must produce a plan with **zero unintended destroys**. Check the plan summary before applying.

## 10. Security

- **No secrets in code, tfvars, or variable defaults.** Fetch from Vault, AWS Secrets Manager, SSM Parameter Store, or CI secret variables.
- Prefer ephemeral resources and write-only arguments (Terraform ≥ 1.10/1.11) where providers support them, so secrets never land in state.
- Least-privilege IAM: build policies with `aws_iam_policy_document` data sources, not inline JSON strings. No `"*"` actions or resources without justification.
- Encryption at rest and in transit enabled by default (S3, EBS, RDS, EFS, SNS, SQS).
- S3: block public access, enforce TLS via bucket policy, enable versioning for important data.
- Security groups: no `0.0.0.0/0` ingress except on intended public ports (80/443 on load balancers). Every rule has a `description`.
- Enable logging/auditing where available (CloudTrail, VPC flow logs, access logs).
- CI authenticates via **short-lived credentials** (OIDC federation, IAM Roles Anywhere, workload identity) — never long-lived access keys.
- Separate plan and apply roles: plan role read-only, apply role scoped to the stack.
- Run static security scanning (Checkov, Trivy, or tfsec) in CI and fix or explicitly suppress findings with a justification comment.

## 11. Tagging

- Apply common tags via provider `default_tags`:
  ```hcl
  provider "aws" {
    region = var.region
    default_tags {
      tags = local.common_tags
    }
  }
  ```
- Merge resource-specific tags: `tags = merge(local.common_tags, { Name = "${local.name_prefix}-api" })` when not using `default_tags`.
- Mandatory tags: `Project`, `Environment`, `Owner`, `ManagedBy`. Enforce via policy or tflint rules.

## 12. Providers

- Configure providers only in root modules.
- Use provider aliases for multi-region / multi-account, and pass them explicitly to modules:
  ```hcl
  provider "aws" {
    alias  = "us_east_1"
    region = "us-east-1"
  }

  module "cdn_cert" {
    source    = "../../modules/acm"
    providers = { aws = aws.us_east_1 }
  }
  ```
- Use `assume_role` in provider config for cross-account access rather than separate credentials.
- Never hardcode credentials in provider blocks.

## 13. Data Sources

- Use data sources to look up existing infrastructure instead of hardcoding IDs (AMIs, VPCs, account ID, region).
- Use `data "aws_caller_identity"` and `data "aws_region"` instead of hardcoding account IDs and regions.
- Filter AMI lookups precisely and pin owners.

## 14. Code Style & Quality

- Run `terraform fmt -recursive` — formatting is non-negotiable.
- Run `terraform validate` on every change.
- Run **tflint** with the relevant ruleset (e.g., `tflint-ruleset-aws`).
- Generate module docs with **terraform-docs** and keep READMEs current.
- Use **pre-commit** hooks: `terraform_fmt`, `terraform_validate`, `terraform_tflint`, `terraform_docs`, `checkov` / `trivy`.
- Order inside a resource block: meta-arguments (`count`/`for_each`/`provider`) first, then arguments, then nested blocks, then `tags`, then `lifecycle`/`depends_on` last.
- Comment the *why*, not the *what*.
- No hardcoded values that differ between environments — they go in variables/tfvars.

## 15. Testing

- Use native `terraform test` (`*.tftest.hcl`) for modules:
  ```hcl
  run "bucket_has_versioning" {
    command = plan

    assert {
      condition     = aws_s3_bucket_versioning.this.versioning_configuration[0].status == "Enabled"
      error_message = "Bucket versioning must be enabled."
    }
  }
  ```
- Use `command = plan` for fast unit-style tests; `command = apply` for integration tests in a sandbox account.
- Use mock providers (`mock_provider`) for tests that shouldn't touch real cloud APIs.
- Every module has at least one working example under `examples/` that is tested in CI.
- Policy-as-code (OPA/Conftest, Sentinel) for organization-wide guardrails on plans.

## 16. CI/CD Workflow

- **Never apply from a laptop to shared environments.** All applies go through the pipeline.
- Pipeline stages:
  1. `fmt -check` → `validate` → `tflint` → security scan
  2. `terraform plan -out=tfplan` on every merge/pull request; post the plan summary as a comment
  3. Manual approval for staging/prod
  4. `terraform apply tfplan` — apply the **exact saved plan**, never re-plan at apply time
- Run `terraform init -input=false` and `plan -input=false -lock-timeout=5m` in CI.
- Use `-detailed-exitcode` on scheduled plans to detect drift (exit code 2 = changes).
- Run scheduled drift-detection plans and alert on unexpected changes.
- Promote changes dev → staging → prod using the same module version.
- Store plan artifacts briefly and treat them as sensitive (they may contain secrets).

## 17. Environments & Configuration

- Same modules, different inputs per environment via `terraform.tfvars` or `<env>.tfvars`.
- Keep environment differences explicit and minimal (sizes, counts, feature flags).
- Prod should never depend on resources in dev/staging.
- Use separate cloud accounts/subscriptions per environment when possible.

## 18. Performance & Maintainability

- Keep each state to a manageable size (roughly hundreds of resources, not thousands) — split large stacks.
- Avoid deeply nested modules (more than 2 levels gets hard to reason about).
- Don't wrap a single resource in a module unless it adds real value (secure defaults, conventions).
- Prefer well-maintained community modules (e.g., `terraform-aws-modules`) over writing from scratch — pin versions and review them.

## AI Assistant Rules

When generating or modifying Terraform in this project:

1. **Always** include `description` and `type` on every variable, and `description` on every output.
2. **Always** use `for_each` instead of `count` for collections.
3. **Always** pin provider and module versions.
4. **Always** use `aws_iam_policy_document` data sources for IAM policies.
5. **Always** use `moved` / `import` / `removed` blocks instead of instructing manual state commands.
6. **Always** enable encryption, block public access, and apply least privilege by default.
7. **Always** produce code that passes `terraform fmt`, `terraform validate`, and `tflint`.
8. **Never** hardcode secrets, credentials, account IDs, regions, or AMI IDs.
9. **Never** put `provider` or `backend` blocks in reusable modules.
10. **Never** use provisioners unless explicitly requested — propose a native alternative.
11. **Never** suggest `terraform apply -auto-approve` against shared environments outside CI.
12. **Never** use `ignore_changes` without a comment explaining why.
13. When a change could **destroy or replace** a resource, call it out explicitly and suggest `create_before_destroy`, `moved`, or `prevent_destroy` as appropriate.
14. When unsure about a provider argument, say so rather than inventing attributes — check the provider documentation for the pinned version.
15. Keep changes minimal and focused; don't reformat or restructure unrelated code.

## Review Checklist

- [ ] `fmt`, `validate`, `tflint`, security scan pass
- [ ] Plan reviewed — no unexpected destroys/replacements
- [ ] Versions pinned, lock file committed
- [ ] No secrets in code, tfvars, or outputs (sensitive values marked)
- [ ] Variables/outputs documented and typed, validations where useful
- [ ] Tags applied
- [ ] IAM least privilege, encryption on, no public exposure
- [ ] Critical stateful resources have `prevent_destroy`
- [ ] README regenerated with terraform-docs
- [ ] Tests/examples updated
